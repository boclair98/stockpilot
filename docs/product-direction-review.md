# StockPilot 제품 방향 검토 · 판단에서 결과까지

## 어떤 서비스로 남길 것인가

**시장은 바로 열리고, 연습은 선택할 수 있으며, 결과는 해석할 필요가 없는 모의투자 서비스.** 초보자에게 가장 먼저 필요한 경험은 기능 목록이 아니라 실제 돈 없이 한 번 판단하고 무엇이 일어났는지 보는 것이다. 재방문자의 빠른 시장 탐색도 같은 기준으로 지킨다.

|대안|가치|의도적으로 택하지 않은 부분|
|---|---|---|
|증권 터미널 확장: 홈에 더 많은 순위·지표·공시|익숙한 사용자의 자료 탐색|기존 시장·전체 종목·비교가 이미 있고, 새 지표는 처음 연습을 끝내지 못하는 문제를 풀지 못한다.|
|초보자 전용 온보딩을 시장보다 앞에|기능 설명 순서 명확|이미 찾을 종목이 있는 사용자를 가로막고, 설명을 읽는 것이 실제 첫 경험이나 차별성은 아니다.|
|시장 우선 + 선택형 과거 시세 실습 + 추적 가능한 주문 결과|기존 탐색을 보존하고 계좌 없이 안전하게 한 번 판단|과거 시세가 누락되면 처음 연습도 막힌다. 그래서 별도 가이드 진입만 바꾸고 시장을 열어 두며, 실패 시 재조회·시장 복귀를 제공한다. 신규 홈 조회·가짜 대체 시세를 쓰지 않는다.|
|현상 유지|작업·배포 부담이 없다|정상 서버 주문 응답을 웹에서 미확인으로 다루는 재현 가능한 결함과 다른 곳에 숨어 있는 첫 연습 흐름을 남긴다.|

## 독립 검토와 결론

- 제품·UX 검토: 가이드가 종목 검색·학습 자료로만 시작하며, 기존 `/practice`는 전체 메뉴의 접힌 선택지다. 기존 시장을 교육 화면으로 바꿀 근거는 없다. 가이드의 한 동작을 실제 체험으로 연결하는 안을 채택했다.
- 구현·데이터 검토: `STOP_LIMIT` 조건에 도달했지만 지정가를 만족하지 않으면 서버는 정상 미체결 `TRIGGERED`를 반환한다. 웹 검증기가 이를 거부하며 재조회로도 풀리지 않는다. 원장이나 주문 정의를 바꾸지 않고 수신·시각 피드백의 계약만 보완하기로 했다.
- 검증·운영 검토: 기존 운영 점검은 빈 가격·부분 카탈로그·대체 캐시에서도 계약이 유효하면 통과했다. 이는 장애 설명이 가능한 읽기 응답이라는 뜻이지 첫 체험 성공이나 새 릴리즈 검증이 아니다. 이번엔 가이드 목적지, 실제 UI 상태, 정상·미확인 주문을 별도 검증한다. 의도적으로 잘못된 응답도 넣어 실패 조건을 확인한다.
- 화면 통합 검증에서 종목코드·시장·거래소·통화와 가격 기록이 일치해도 응답에 표시용 이름이 없거나 표기가 다르면 자료를 거부하는 문제를 확인했다. 이름은 고유 식별자가 아니므로 네 필드만 계약과 대조한다. 표시 이름 없이 가격을 판별하고 다른 종목의 응답은 계속 거부하는 검사를 추가했다.
- 다른 실제 결함: 매도 가능 수량은 화면이 최근 30건만 보고 계산해 오래된 예약을 놓칠 수 있다. 제출 시 서버는 전체 예약을 확인해 원장에는 잘못 반영되지 않는다. 화면만 맞는 척 고치거나 건수 상한을 늘리지 않는다. 서버 집계와 30건 초과·계정/거래소 분리의 PostgreSQL 검증이 필요한 별도 후보로 기록한다.
- 운영 후속: Redis 연결은 시작 신호와 실제 가용성이 다를 수 있다. 캐시 상태 검증과 시세 동시접속 수용량은 본 UX 변경과 독립이며, 이번 검증을 부하·SLO 인증으로 간주하지 않는다.

## 우선 사용자 여정과 거절 조건

1. 시작 가이드의 ‘로그인 없이 과거 시세로 연습’ → 과거 시세 화면. 초보자가 읽기와 직접 체험을 구분할 수 있어야 하고, 시장으로 가는 기존 선택도 보인다.
2. 날짜와 해당 시점 종가를 확인 → 연습으로 한 주를 사거나 거래 없이 하루 진행 → 다음 날짜와 평가액을 확인. 계좌·주문 API 쓰기가 없어야 하며 이 화면을 벗어나면 연습 기록을 저장하지 않는다는 안내가 먼저 보인다. 미래 시점 가격은 차트에 먼저 나타나지 않는다.
3. 모의계좌 주문 또는 복구 조회에서 조건을 충족한 미체결 상태를 받으면 ‘조건 충족 · 체결 대기’와 매매 기록 이동을 보여준다. 접수된 주문을 다시 보내지 않고, 누락되거나 알 수 없는 응답만 확인이 필요한 상태로 남긴다.
4. 과거 자료 실패는 오류·다시 불러오기 및 시장 복귀를 제공한다. 계산·실제 시세·인증을 바꾸지 않는다. 출시 전에는 응답 계약·실제 화면·운영 준비 신호를 구별하고, 새 배포 권한과 실제 검증이 필요하다.

[GOV.UK의 결과 안내](https://design-system.service.gov.uk/patterns/confirmation-pages/)와 [당근 SEED의 피드백](https://seed-design.io/foundations/feedback)은 현재 상태와 다음 행동을 연결하는 데 참고했다. [토스 Frontend Fundamentals](https://github.com/toss/frontend-fundamentals)의 예측 가능성을 따라 수신 검증, 상태 설명, UI 동작을 구분하고, [김영한의 DB 실무 자료](https://www.inflearn.com/course/스프링-db-2)가 다루는 DB 연동 검증처럼 접수·읽기 복구·취소 전후의 모의원장을 비교한다. 실제 토스 팀이나 김영한 개발자가 설계·승인한 것은 아니며 사용자 조사나 활성 지표도 없다.

## 회귀 검사

- `frontend/scripts/verify-release-safety.cjs`는 미체결 응답 수락과 잘못된 응답 거부, 재제출 금지의 단위 계약을 확인한다.
- `frontend/scripts/verify-first-practice.mjs`는 격리 브라우저에서 가이드 → 연습 → 다음 거래일, 오류 후 복구, 시장 복귀 링크와 반응형을 검사한다. `--production`은 지정된 운영 URL의 읽기 전용 확인이다.
- `frontend/scripts/verify-condition-receipt.mjs`는 루프백 프리뷰에서만 사용하며 주문 응답을 브라우저 안에서 가로챈다. 정상 응답·응답 유실 후 동일 키 조회가 미체결로 표시되는지 확인한다. 실제 주문은 보내지 않는다.
- `backend/unit_tests/test_stop_limit_receipt.py`는 격리 SQLite에서 FastAPI 접수 → 동일 키 조회 → 취소 전후의 원장과 상태를 확인한다. PostgreSQL 동시성 검증을 대체하지 않는다.
